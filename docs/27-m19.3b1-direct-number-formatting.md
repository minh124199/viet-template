## 1. STARTING STATE

Following the completion of Milestone M19.3b (Streaming Output Allocation & UTF-8 Formatting Qualification, documented in [`docs/26-m19.3b-output-allocation-qualification.md`](26-m19.3b-output-allocation-qualification.md)), the project established that:
1. `byte[]` allocations accounted for $\approx 33.11\%$ of allocation volume during template rendering.
2. 99.6% of `byte[]` volume in unpooled streaming stems from unpooled $8\text{ KB}$ buffer creation and `ByteArrayOutputStream` resizing.
3. In numeric rendering paths, `NumberFormatting.formatInt` and `NumberFormatting.formatLong` suffered from an avoidable temporary array allocation leak:
   - `formatInt` allocated `byte[] temp = new byte[11]` on every call ($32.000\text{ B/op}$ in 64-bit HotSpot).
   - `formatLong` allocated `byte[] temp = new byte[20]` on every call ($40.000\text{ B/op}$ in 64-bit HotSpot).

Milestone M19.3b formally promoted **Candidate 1: Zero-Allocation Direct Primitive Number Formatting** for immediate production implementation under Milestone M19.3b.1.

The starting repository state was verified clean at baseline commit `19a5f0d` on branch `main`. Scope was strictly restricted to `formatInt` and `formatLong` in `NumberFormatting.java` and associated tests, keeping all other runtime, parser, compiler, and SPI components frozen.

## 3. OLD FORMATTER ARCHITECTURE

The legacy formatting methods in [`NumberFormatting.java`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-runtime/src/main/java/io/github/minh124199/viettemplate/runtime/NumberFormatting.java) were structured as follows:

```java
// Legacy formatInt (Lines 99-112)
byte[] temp = new byte[11];
int pos = 11;
boolean negative = value < 0;
int v = negative ? -value : value;
while (v > 0) {
  temp[--pos] = (byte) ('0' + (v % 10));
  v /= 10;
}
if (negative) {
  temp[--pos] = '-';
}
int len = 11 - pos;
System.arraycopy(temp, pos, target, offset, len);
return len;
```

### Inherent Deficiencies:
1. **Per-Invocation Heap Allocation**: Every integer formatted allocated an 11-byte array ($24\text{ bytes header} + 11\text{ bytes} + 5\text{ bytes padding} = 32\text{ bytes}$). Every long formatted allocated a 20-byte array ($24\text{ bytes header} + 20\text{ bytes} = 40\text{ bytes}$).
2. **Double Memory Touch & Copying**: Digits were extracted backwards into `temp`, and then copied via `System.arraycopy` into `target`. This incurred JNI/intrinsic call overhead and cache pollution.
3. **Escaped Allocation in JFR**: In tight loops (e.g. a table with 50 rows of IDs), thousands of short-lived byte arrays flooded Eden space, triggering frequent minor GC cycles.

## 4. NEW DIRECT FORMATTER ALGORITHM

The new production implementation replaces intermediate buffers with **direct backward decimal encoding** directly into the caller's `target` byte array:

```java
// Production formatInt (NumberFormatting.java)
public static int formatInt(int value, byte[] target, int offset) {
  if (value == Integer.MIN_VALUE) {
    System.arraycopy(INT_MIN_BYTES, 0, target, offset, INT_MIN_BYTES.length);
    return INT_MIN_BYTES.length;
  }
  if (value == 0) {
    target[offset] = '0';
    return 1;
  }
  boolean negative = value < 0;
  int v = negative ? -value : value;
  int len = stringSize(value);
  if (negative) {
    target[offset] = '-';
  }
  int pos = offset + len;
  while (v > 0) {
    target[--pos] = (byte) ('0' + (v % 10));
    v /= 10;
  }
  return len;
}
```

### Key Algorithmic Properties:
1. **Pre-Computed Length via `stringSize()`**: Uses the branch-free `stringSize(int)` and `stringSize(long)` lookup methods already present and battle-tested in `NumberFormatting`.
2. **Deterministic Placement**: The negative sign (`'-'`) is placed immediately at `target[offset]`.
3. **Backward In-Place Digit Fill**: Digits are written from `target[offset + len - 1]` down to `target[offset + (negative ? 1 : 0)]`.
4. **Boundary Preservation**: `Integer.MIN_VALUE` and `Long.MIN_VALUE` continue using pre-allocated constant byte arrays (`INT_MIN_BYTES`, `LONG_MIN_BYTES`) since `-Integer.MIN_VALUE` overflows 32-bit two's complement.
5. **Zero Allocation**: $0.000\text{ B/op}$ allocated. Zero temporary arrays, zero objects.

   - Confirmed no `ArrayIndexOutOfBoundsException` occurs for any boundary or extreme value.
3. **Sequential Target Reuse**: Tested multiple sequential invocations writing into the same array at `offset += len`, validating real-world streaming buffer append behavior.
