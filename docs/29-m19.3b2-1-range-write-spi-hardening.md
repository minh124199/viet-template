## 2. Why M19.3b.2.1 Exists

PR #13 achieved its primary mission: `HtmlTextEscaper` no longer calls `subSequence()` or materializes temporary substring segments on the heap. However, two follow-up architectural items remained:

1. **Public SPI Contract Formalization**:
   `TemplateOutput.write(CharSequence value, int start, int end)` was introduced as a default interface method in `viet-template-api`. Because `TemplateOutput` is the primary public SPI for custom template output targets (servlets, reactive bridges, memory buffers), this method is now public API. Its edge-case semantics (`null`, empty range, bounds checking via `Objects.checkFromToIndex`, surrogate pair boundaries, and third-party implementor backward compatibility) required formal specification and exhaustive contract testing.

2. **Writer-Backed Range Allocation Cleanup**:
   In `WriterTemplateOutput.write(CharSequence value, int start, int end)`, String inputs bypassed allocation via `writer.write(s, start, end - start)`. However, non-String `CharSequence` inputs (such as `StringBuilder`, `StringBuffer`, or custom token sequences) executed:
   ```java
   char[] buf = new char[Math.min(len, 1024)];
   ```
   This allocated a temporary `char[]` array on every non-String range write. Milestone M19.3b.2.1 systematically evaluates non-String range write strategies to eliminate or minimize this allocation without regressing Writer performance.

## 4. Default Range-Write Contract

In `viet-template-api/src/main/java/io/github/minh124199/viettemplate/api/TemplateOutput.java`, the contract is formalized as follows:

```java
  /**
   * Writes a subsequence of the specified character sequence to this output.
   *
   * <p>An indexing interval of {@code [start, end)} is used: {@code start} is inclusive, and {@code
   * end} is exclusive. The number of characters written is {@code end - start}.
   *
   * <p>Contract guarantees:
   *
   * <ul>
   *   <li><b>Null Safety:</b> If {@code value} is {@code null}, this method is a safe no-op and
   *       returns immediately without error.
   *   <li><b>Empty Range:</b> If {@code start == end}, this method is a safe no-op and returns
   *       immediately without writing any characters.
   *   <li><b>Bounds Validation:</b> Throws {@link IndexOutOfBoundsException} if {@code start < 0},
   *       {@code end < start}, or {@code end > value.length()}, matching {@link
   *       Objects#checkFromToIndex(int, int, int)}.
   *   <li><b>Backward Compatibility:</b> The default implementation delegates to {@link
   *       #write(char)} in a sequential loop from {@code start} to {@code end - 1}. Custom {@code
   *       TemplateOutput} implementations may override this method with specialized, zero-allocation
   *       batch operations.
   * </ul>
   *
   * @param value the character sequence to write from, or {@code null}
   * @param start the beginning index, inclusive
   * @param end the ending index, exclusive
   * @throws IndexOutOfBoundsException if {@code start < 0}, {@code end < start}, or {@code end >
   *     value.length()}
   * @throws IOException if an I/O error occurs
   * @since 0.2.1
   */
  default void write(CharSequence value, int start, int end) throws IOException {
    if (value == null) {
      return;
    }
    Objects.checkFromToIndex(start, end, value.length());
    for (int i = start; i < end; i++) {
      write(value.charAt(i));
    }
  }
```

## 5. Implementation Audit

All production implementations were audited against the formal contract:

1. **`StringTemplateOutput`**:
   - Delegates directly to `builder.append(value, start, end)` after validating `value != null` and `Objects.checkFromToIndex`.
   - **Zero heap allocation**; exact match for `[start, end)`.
2. **`Utf8OutputStreamTemplateOutput`**:
   - Performs direct bit-level UTF-8 encoding from `value.charAt(i)` into its internal 8KB byte buffer.
   - Accurately checks surrogate pairs (`Character.isHighSurrogate(c)` with `i + 1 < end && Character.isLowSurrogate(value.charAt(i + 1))`).
   - Slices ending on high surrogates emit the standard Unicode replacement byte sequence (`0xEF, 0xBF, 0xBD`), preserving existing error-resilience invariants.
   - **Zero heap allocation**.
3. **`CountingTemplateOutput`**:
   - Calls `Objects.checkFromToIndex(start, end, value.length())`.
   - Calls `checkLimit(end - start)`, accurately debiting the budget by the exact logical character length before delegating to `delegate.write(value, start, end)`.
   - No under-counting, no double-counting.
4. **`WriterTemplateOutput`**:
   - For `String`: `writer.write(s, start, end - start)` (zero allocation).
   - For non-`String`: Evaluated under Sections 6–9.

## 6. Writer Residual Allocation

In M19.3b.2, non-String range writes in `WriterTemplateOutput` executed:
```java
int len = end - start;
char[] buf = new char[Math.min(len, 1024)];
```
On inputs like `StringBuilder`, each range write allocated a fresh `char[]` buffer:
- For an 8-character slice: 32 bytes allocated.
- For a 32-character slice: 80 bytes allocated.
- For a 128-character slice: 272 bytes allocated.
- For a 1024-character slice: 2064 bytes allocated.

While `String` inputs are the common case, non-String `CharSequence` instances are frequently used in custom buffer pipelines, AST evaluations, and formatters.

---

## 7. Strategy A — Current Chunk Array

**Design**:
Allocates `char[] buf = new char[Math.min(len, 1024)]` on every invocation. Slices are copied in chunks of up to 1024 chars and written via `writer.write(buf, 0, chunk)`.

- **Advantages**: Acquires `Writer` monitor only $\lceil len / 1024 \rceil$ times. High batch throughput on large buffers.
- **Disadvantages**: Unbounded heap churn under heavy rendering; per-call allocation ($32\text{--}2064\text{ B/op}$).

---

## 8. Strategy B — Direct Char Loop

**Design**:
```java
for (int i = start; i < end; i++) {
  writer.write(value.charAt(i));
}
```

- **Advantages**: $0.000\text{ B/op}$ temporary allocation; 0 bytes retained memory; simplest possible code.
- **Disadvantages**: On standard Java `Writer` classes (`StringWriter`, `BufferedWriter`, `OutputStreamWriter`), `writer.write(int c)` acquires `synchronized (lock)` on **every single character**. For an 80-character HTML slice, this executes 80 lock acquisitions and releases.

---

## 9. Strategy C — Output-Owned Buffer

**Design**:
`WriterTemplateOutput` manages an instance-confined `char[] scratchBuffer` (size 1024).
To eliminate memory overhead for String-only workloads, the buffer is allocated **lazily** on first non-String range write:
```java
if (scratchBuffer == null) {
  scratchBuffer = new char[SCRATCH_BUFFER_SIZE];
}
```

- **Advantages**:
  - $0.000\text{ B/op}$ steady-state allocation on non-String writes.
  - Exactly 1 lock acquisition per 1024 chars in `writer.write(scratchBuffer, 0, chunk)`.
  - **Zero retained memory** for String-only template renders (lazy allocation).
- **Disadvantages**: Retains $\approx 2064\text{ bytes}$ per `WriterTemplateOutput` instance *only if* a non-empty non-String `CharSequence` is written.

> [!CAUTION]
> **The Direct Char Loop Synchronization Pitfall**:
> On an unconstrained `NoOpWriter`, `DIRECT_CHAR_LOOP` is $37\text{--}50\%$ faster than array buffering because it avoids array writes. However, on any standard Java `Writer` (`StringWriter`, `BufferedWriter`, `OutputStreamWriter`, servlet response writer), `Writer.write(int)` synchronizes on `lock`.
> For an average 80-char HTML slice, `DIRECT_CHAR_LOOP` causes an **80.8% to 94.0% throughput collapse**. This violates the $\le 10\%$ hard regression tolerance. Strategy B is therefore **disqualified**.
