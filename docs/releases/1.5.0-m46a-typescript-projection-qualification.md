## 1. Executive Summary & Qualification Verdict

Milestone M46A investigated, prototyped, and qualified the architecture for **Schema-to-Client TypeScript Contract Projection** for Viet Template 1.5. The objective was to design the smallest, deterministic, frontend-framework-neutral architecture projecting canonical server-side template/model contracts into high-quality TypeScript declarations (`.d.ts`), proving:
1. **Byte-for-byte cross-run determinism** (zero timestamps, sorted declarations, stable SHA-256).
2. **Incremental write avoidance** (`writeIfChanged`) preserving filesystem modification times (`mtime`) on unchanged outputs.
3. **Safe generated-output ownership and cleanup** (`cleanStaleOutputs`) removing only owned stale `.d.ts` files while strictly leaving foreign user files untouched.
4. **Deterministic collision handling** for identical class simple names in different packages.
5. **Safe recursive type projections** without circular resolution or stack overflow.
6. **Strict nullability mapping** with TypeScript `--strict` enforcement.
7. **1:1 runtime serialization parity** with `ClientData` and `SimpleJsonSerializer` (including JSON array projections for collections/sets, ISO-8601 strings for temporal types, and string literal unions for enums).
8. **Fail-closed security boundaries** filtering restricted classes and methods via `MemberAccessPolicy`.
9. **Zero Node/npm runtime dependency** in Java builds or runtime.
10. **Frontend framework neutrality** producing pure TypeScript declaration files.

### Authoritative Verdict: `GO`

The qualification verdict is an unqualified **`GO`**.

All 14 bounded prototype tests implemented in `M46ATypeScriptProjectionQualificationTest.java` passed cleanly with 100% compliance. Real `tsc --noEmit` validation confirmed that generated `.d.ts` files are syntactically and semantically sound, successfully reject property typos (`employee.nmae`), enforce null checking, and support recursive graph structures.

## 3. Input Contract Decision (Candidate D: Hybrid Normalization)

Four candidate projection pipelines were evaluated:
- **Candidate A: Direct Java Reflection to TypeScript**: Bypasses intermediate schema, emits TS directly from Java reflection. *Rejected*: Misses template parameter contracts, duplicates member resolution logic, cannot consume JSON schemas.
- **Candidate B: Direct TemplateContract to TypeScript**: Projects only `TemplateContract` without normalizing complex nested Java types. *Rejected*: Fails to handle deep nested domain records/beans and recursive structures.
- **Candidate C: JSON Schema Intermediate Files**: Generates intermediate `.json` schema files on disk and transforms them. *Rejected*: Excessive I/O overhead, synchronization fragility, and complex stale-file management.
- **Candidate D: Hybrid Normalization via CanonicalSchemaModel (ADOPTED)**:
  `TemplateContract` and Java model types are normalized into in-memory `CanonicalSchemaModel` instances via `JavaModelSchemaImporter`, which are then emitted into deterministic `.d.ts` declarations by a pure-Java emitter.
  - *Rationale*: Reuses existing validated schema infrastructure, supports both template parameters and deep domain classes, requires zero disk intermediate steps, and guarantees uniform type mapping.

## 4. Server-Side Semantic Types vs. Serialized Client Data Contract

A critical architectural distinction verified during qualification is the difference between server-side template contracts and client-side data projections:

1. **Server-Side Template Contract**:
   - In server VTL templates, Java objects retain their computational behavior (e.g. calling `$employee.calculateAnnualBonus()`).
   - Members include public zero-arg methods, getters, and record components.
2. **Client-Side Data Contract**:
   - Client-rendered islands receive serialized JSON payloads over the wire (`ClientData`).
   - JSON payloads contain **data properties only**; methods are never serialized.
   - Non-primitive types are converted according to JSON serialization rules (e.g., `Set<T>` becomes an array `[...]`, `Instant` becomes an ISO-8601 string).
3. **Projection Boundary Decision**:
   - Generated `.d.ts` declarations model the **serialized client data shape**, not server-side Java methods.
   - Property names strictly match JSON property names (record components, getter property names).

## 6. Output Organization, Naming & File Strategy

Four output file strategies were evaluated:

| Strategy | DX / Ergonomics | Incremental Cacheability | Collision Isolation | Stale Cleanup Safety | Verdict |
|:---|:---:|:---:|:---:|:---:|:---:|
| **Single Monolithic File (`contracts.d.ts`)** | Poor (mega-file merge conflicts) | Poor (any change rewrites file) | Complex (global namespace) | Trivial (single file) | **REJECTED** |
| **Per-Model Files (`Employee.d.ts`)** | Medium (fragmented imports) | Medium (deep dependency tree) | Medium | Risky (hundreds of loose files) | **REJECTED** |
| **Per-Template Declarations (`index.vtl.d.ts`)** | **High (1:1 with template)** | **High (isolated per template)** | **High (template-scoped)** | **High (1:1 template lifecycle)** | **ADOPTED (Primary)** |
| **Hybrid (Per-Template + Shared Common)** | High | Medium | Medium (cross-file links) | High | **RESERVED (Optional)** |

**Decision**: The generator adopts **Per-Template Declarations** as the primary strategy. A template at `src/main/resources/templates/employees/detail.vtl` projects to `detail.vtl.d.ts` containing `DetailContract` and referenced dependent interfaces.

## 7. Package Collision & Disambiguation Policy

When multiple Java models with the same simple class name from different packages are used within projected declarations (e.g. `com.example.hr.Employee` and `com.example.payroll.Employee`):

1. **Detection**: Types are grouped by simple class name during schema processing.
2. **Deduplication**: Aliases pointing to the same underlying FQCN within the same template contract are consolidated (preventing false self-collisions).
3. **Disambiguation Rule**: If distinct FQCNs share a simple name, the simple name is prefixed with sanitized package components in camel-case (e.g. `Hr_Employee` and `Payroll_Employee`).
4. **Ordering**: Disambiguated types are sorted lexicographically by FQCN to guarantee stable output order.

## 8. Determinism & Byte-for-Byte Reproducibility

To prevent spurious version-control churn and maintain reproducible build outputs:
- **No Timestamps**: Generated headers contain tool identification (`Generated by Viet Template`) but strictly omit generation timestamps and host machine file paths.
- **Canonical Line Endings**: All output is normalized to Unix LF (`\n`).
- **Encoding**: Output is strictly encoded in UTF-8 without BOM.
- **Sorted Declarations**: Interfaces and properties within interfaces are emitted in alphabetical order.
- **Validation**: Prototype test 07 executed 100 consecutive generation cycles across varying JVM invocations and verified identical SHA-256 checksums on all outputs.

---

## 9. Incremental Generation & Write Avoidance (`writeIfChanged`)

Modern frontend build tools (Vite, Rollup, Webpack, SvelteKit) use filesystem watchers that trigger hot-module-replacement (HMR) or cold rebuilds on file timestamp changes (`mtime`).
- The generator implements `writeIfChanged(Path target, String content)`:
  1. Checks if the target file exists.
  2. If it exists, reads existing content into memory.
  3. If existing content matches the prospective content byte-for-byte, the disk write is **completely bypassed**, preserving `mtime`.
  4. If content differs or file is absent, writes atomically.
- Validated in Prototype test 08: `Files.getLastModifiedTime()` remains unchanged after a no-op regeneration cycle.

---

## 10. Safe Output Ownership & Stale Cleanup (`cleanStaleOutputs`)

When templates are deleted, renamed, or moved, corresponding generated declaration files must be cleaned up without risking developer source code:
- **Ownership Invariant**: The generator maintains an explicit set of owned paths generated in the current build.
- **Candidate Scope**: Stale scan is restricted to managed generation directories matching `*.vtl.d.ts`.
- **Foreign File Protection**: Hand-written developer files (e.g. `manual.ts`, `custom.d.ts`) located in the output directory are recognized as unowned and are strictly preserved.
- Validated in Prototype test 09: Only deleted template `.d.ts` files are removed; foreign `.ts` and `.d.ts` files remain intact.

---

## 11. Cross-Platform Path Normalization

- Relative template paths are normalized by converting all Windows backslashes (`\`) to forward slashes (`/`).
- Path traversal sequences (`..`) and absolute path escapes are strictly validated and rejected before file resolution.
- Validated in Prototype test 10: `templates\employees\index.vtl` and `templates/employees/index.vtl` resolve to the exact same contract identity `templates/employees/index.vtl`.

---

## 12. Fail-Closed Security Analysis & MemberAccessPolicy Integration

The reflection introspection layer in `M46APrototypeTypeScriptProjector` integrates directly with Viet Template's security model:
- **Filtered Classes**: Introspection strictly excludes internal JVM types: `java.lang.Class`, `java.lang.ClassLoader`, `java.lang.Thread`, `java.lang.reflect.*`.
- **Filtered Methods**: Methods like `getClass()`, `wait()`, `notify()`, `hashCode()`, `equals()` are never projected into client TypeScript interfaces.
- **Policy Enforcement**: Any member rejected by `MemberAccessPolicy` is omitted from the projected schema.
- Validated in Prototype test 11: `SecuritySensitiveBean` projects only legitimate business properties (`data`); `getClass()`, `classLoader`, and `thread` are completely omitted.
