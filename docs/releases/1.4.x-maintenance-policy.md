# Viet Template 1.4.x Maintenance Policy & Patch Governance

> **Status:** Canonical Maintenance Governance & Machine-Enforced Policy  
> **Applicability:** Viet Template 1.4.x Line (1.4.1, 1.4.2, etc.)  
> **Release Baseline:** `v1.4.0` (commit `1ee485beee4b7588dd154881ede1e76985e339dc`, tag object `615ffa9ea291fbd9226e040fd321f7ed018bd01a`)  
> **Permanent Compatibility Floor:** `v1.0.0` (`b951021e9975b8e8103b2402dc244b32a96afaa8`)  
> **Verification Command:** `python3 scripts/verify-release-line-compatibility.py --baseline 1.4.0 --candidate HEAD --policy patch`

---

## 1. Executive Summary & Purpose

Following the General Availability release of Viet Template 1.4.0, the `1.4.x` line enters a strictly governed maintenance phase. The goal of this policy is to guarantee that future patch releases (`1.4.1`, `1.4.2`, etc.) cannot accidentally introduce feature-level changes, expand public API/SPI surfaces, or alter the newly stabilized contracts introduced in 1.4.0 (including the Frontend Asset Integration subsystem), while continuing to allow legitimate bug fixes, security hardening, and semantics-preserving performance improvements.

## 2. Core Compatibility Model

Viet Template enforces a layered compatibility architecture:

```text
                     Permanent Compatibility Floor
                                v1.0.0
                                  │
                                  ▼
                     Existing 1.0 API/ABI Baselines
                                  │
                                  ▼
                      All Future Viet Template
                                  │
                    ┌─────────────┴─────────────┐
                    ▼                           ▼
             Feature Releases            Patch Releases
             1.5.0, 1.6.0...             1.4.1, 1.4.2...
                    │                           │
                    │                           ▼
                    │                  Exact v1.4.0 Contract
                    │                           │
                    │                   NO feature drift
                    │                   NO API expansion
                    │                   NO compatibility loss
                    ▼
          May add backwards-compatible
              new functionality
```

### 2.1 Permanent Floor vs Maintenance Baseline

1. **Permanent Compatibility Floor (`v1.0.0`)**:
   - Recorded in [`config/compatibility/1.0.0-compatibility-baseline.json`](../../config/compatibility/1.0.0-compatibility-baseline.json) and [`config/api-baseline/1.0-*.txt`](../../config/api-baseline/).
   - Historically immutable evidence protecting core language semantics, TCK features, diagnostic codes, and runtime ABI.
   - Enforced by `python3 scripts/verify-compatibility-baseline.py`.

2. **Maintenance Baseline (`v1.4.0`)**:
   - Recorded in [`config/compatibility/1.4.0-release-baseline.json`](../../config/compatibility/1.4.0-release-baseline.json) and [`config/api-baseline/1.4.0-*.txt`](../../config/api-baseline/).
   - Locks the exact public surface snapshot released at `v1.4.0`.
   - Protects members, classes, entrypoints, configuration keys, and published coordinates from feature drift.
   - Enforced by `python3 scripts/verify-release-line-compatibility.py`.

## 4. Change Classification & Release Routing

Every candidate change proposed for `1.4.x` is classified into one of three categories:

### 4.1 `PATCH_ALLOWED` (Eligible for 1.4.1+)

Changes permitted in a patch release:
- Bug fixes in existing implementation methods.
- Corrected edge-case handling preserving signatures.
- Security hardening (e.g. enhanced validation, tighter escaping) accompanied by vulnerability rationale and regression tests (`PATCH_ALLOWED_SECURITY`).
- Semantics-preserving performance optimizations backed by JMH benchmark evidence (`PATCH_ALLOWED_PERFORMANCE`).
- Documentation clarifications and typo corrections.
- Test hardening and CI reliability improvements.
- Release infrastructure and build script corrections.

### 4.2 `MINOR_RELEASE_REQUIRED` (Must Route to 1.5.0+)

Changes that expand capabilities in a backwards-compatible manner:
- Adding a new `STABLE_API` or `STABLE_SPI` class, interface, or record.
- Adding a new public or protected method, constructor, or field to an existing stable class.
- Adding a new constant to an existing public enum.
- Adding a new `FRAMEWORK_ENTRYPOINT` (e.g. new auto-configuration class).
- Adding a new public framework configuration key.
- Adding a new published module or Maven coordinate.
- Adding new template language syntax or directives.
- Introducing a new frontend framework provider or tooling integration.

> **Routing Rule**: If `verify-release-line-compatibility.py` reports `MINOR_RELEASE_REQUIRED`, maintainers MUST target the next minor line (`1.5.0`) rather than updating the baseline to bypass the check.

### 4.3 `MAJOR_RELEASE_REQUIRED` (Must Route to 2.0.0+)

Changes that break binary or source compatibility:
- Removing or renaming any `STABLE_API` or `STABLE_SPI` type.
- Removing or renaming any public/protected method, constructor, or field.
- Incompatible signature changes (changing return types, parameter types, or checked exceptions).
- Adding abstract methods to an existing `STABLE_SPI` interface (breaks third-party implementors).
- Changing class modifiers incompatibly (e.g. non-final class becoming final, non-sealed becoming sealed).
- Removing an existing framework configuration key.
- Removing or renaming a published Maven artifact.
- Raising the minimum Java baseline above Java 21.

## 5. Maintenance Branching Strategy

Viet Template follows an on-demand maintenance branch model:

```text
v1.4.0 Tag
    │
    ├──────────────── release/1.4 (created when main advances to 1.5.0-SNAPSHOT)
    │                      │
    │                  1.4.1 / 1.4.2 patch releases
    │                      │
    │                      ▼ (cherry-pick / merge forward)
    └──────────────── main
                           │
                       1.5.0-SNAPSHOT (active minor development)
```

1. **Active Maintenance Line (`release/1.4`)**:
   - The dedicated `release/1.4` maintenance branch was established from commit `5498280740cfd6b4cf5711d496c2f2250ada83ba` (pre-1.5 `main` immediately following merged PR #95).
   - **Branch Provenance Rationale**: Rather than branching directly from raw `v1.4.0` (which predated PR #95 maintenance tooling), branching from the verified pre-1.5 baseline ensures `release/1.4` contains all post-release patch-governance scripts, frozen baseline manifests, and CI enforcement tooling while preserving exact `v1.4.0` product runtime behavior and tracking `1.4.1-SNAPSHOT`.
   - `release/1.4` is active on `origin` and strictly governed by `python3 scripts/verify-release-line-compatibility.py --baseline 1.4.0 --candidate HEAD --policy patch`.
2. **Transition of `main` to 1.5.0-SNAPSHOT**:
   - With the establishment of `release/1.4`, `main` has transitioned to `1.5.0-SNAPSHOT` for active minor feature development (starting with Milestone M44).
   - On `main`, compatibility enforcement routes to `--policy minor`, allowing backwards-compatible additive capabilities while strictly prohibiting breaking API/SPI changes.
3. **Forward Reconciliation Invariant**:
   - Every patch fix committed to `release/1.4` must be immediately forward-reconciled into `main` via cherry-pick or forward merge to ensure bug fixes never regress in `1.5.0+`.

## 6. Verification & CI Enforcement

### 6.1 Checking Patch Eligibility

Maintainers can verify whether candidate changes comply with 1.4.x patch policy:

```bash
# Verify working tree or HEAD against 1.4.0 baseline under patch policy:
python3 scripts/verify-release-line-compatibility.py \
  --baseline 1.4.0 \
  --candidate HEAD \
  --policy patch
```

### 6.2 Pre-Release Verification Matrix

Before tagging any future `v1.4.1` patch release, the following full governance matrix must pass:

```bash
# 1. 1.0 Permanent Compatibility Floor
python3 scripts/verify-compatibility-baseline.py

# 2. 1.4.x Maintenance Line Policy Gate
python3 scripts/verify-release-line-compatibility.py --baseline 1.4.0 --candidate HEAD --policy patch

# 3. Public Surface & API Classification
python3 scripts/verify-public-surface-classification.py
python3 scripts/verify-api-compatibility.py

# 4. Generated Runtime ABI & Diagnostic Codes
python3 scripts/verify-generated-abi.py
python3 scripts/verify-diagnostic-codes.py

# 5. Architecture & Publication Topology
python3 scripts/verify-framework-entrypoints.py
python3 scripts/verify-cross-module-contracts.py
python3 scripts/verify-release-metadata.py

# 6. Unit & Parity Suites
python3 -m unittest discover -s scripts/tests -v
python3 scripts/verify-build-parity.py
python3 scripts/verify-documentation.py

# 7. Dual Build Cleanliness
./mvnw spotless:check test -B
./gradlew spotlessCheck test --no-daemon
```

The 1.4.0 baseline files:
- `config/compatibility/1.4.0-release-baseline.json`
- `config/api-baseline/1.4.0-*.txt`
- `config/compatibility/framework-configuration-keys-1.4.json`

represent **frozen released history**. They MUST NOT be edited or regenerated in candidate pull requests to force a failing compatibility check to pass. Any PR attempting to modify these baseline files fails closed in CI.
