## 1. Executive Summary & Qualification Verdict

Milestone M45A investigated, prototyped, and qualified the architecture for **Optional Typed Template Parameters & Expression Type Propagation** for Viet Template 1.5. The objective was to design the smallest, safest, backwards-compatible type-intelligence architecture supporting optional template parameter declarations, compile-time expression type propagation, compile-time diagnostics, LSP type intelligence, and future TypeScript projection, while preserving:
1. **100% dynamic Velocity (VTL) compatibility** for existing untyped templates.
2. **Runtime dynamic dispatch fallback** whenever types are undeclared or unresolvable.
3. **Fail-closed security invariants** governed by `MemberAccessPolicy` and `LinkerAccessPolicy`.
4. **Java 21 minimum compiler baseline** and GraalVM / Mandrel native image compatibility.
5. **Zero Node/npm runtime dependency** across all production modules.

### Authoritative Verdict: `GO`

The qualification verdict is an unqualified **`GO`**.

Comprehensive auditing and prototype implementations across parser, semantic analyzer, security sandbox, diagnostics, differential rendering guard, and performance benchmarks confirmed that:
- **Syntax Selection**: **Candidate A (`#param(Type $var)`)** is the definitive winner across all criteria (familiarity to Java/Spring/Quarkus engineers, clean token boundary separation via `$`, standard directive syntax, unambiguous prologue grammar).
- **Architecture Reuse**: Extensive core infrastructure already exists in the repository! `TemplateContract`, `TemplateParameter`, and `TemplateType` exist in `viet-template-api`; `VType` and `VtlSemanticAnalyzer` in `viet-template-language-vtl` already provide flow-sensitive type inference and diagnostic emission; `IrTemplate` already models parameters; and `CanonicalSchemaModel` in `viet-template-vtl-interpreter` already defines JSON schema and TypeScript `.d.ts` projection formats.
- **Zero Runtime Overhead**: Untyped templates experience zero runtime overhead and undergo identical AST lowering and execution.
- **Fail-Closed Security**: Declaring types provides zero privilege escalation. `MemberAccessPolicy.standard()` blocks `getClass()`, `ClassLoader`, reflection, and restricted members at compile time (`VTLSEC:2401`) and runtime identically.
- **Performance Throughput**: Full pipeline compilation (scanning, parsing, type propagation, and diagnostic analysis) executes in ~0.5 ms for small templates (budget < 2.0 ms), ~8-10 ms for medium (~50 line) templates (budget < 20.0 ms), and ~30-34 ms for large (~300 line) templates (budget < 50.0 ms), fitting seamlessly into standard IDE keystroke latencies (< 50-100 ms) with zero steady-state rendering runtime overhead.

## 3. Directive Naming Collision Audit & Velocity Compatibility Analysis

### 3.1 Directive Naming Collision Audit (Requirement 9)
To ensure `#param` does not silently collide with existing directives, macros, or extensions, an audit was conducted across all modules:
1. **Built-in VTL Directives**: Current built-in directives in `VtlParser` are `#set`, `#if`, `#elseif`, `#else`, `#end`, `#foreach`, `#include`, `#parse`, `#break`, `#stop`, `#evaluate`, `#define`, `#macro`. The name `param` is **not** a built-in directive.
2. **Repository Test Fixtures & TCK**: A full grep of the repository, TCK suites, and example templates revealed **zero** uses of `#param` or macros named `#macro(param ...)`.
3. **Apache Velocity Standard Directives**: Apache Velocity 1.7 / 2.x standard directives do not include `#param`.
4. **Velocity Directive Collision Assessment**: If an existing application template defined a custom Velocity macro named `param`, moving to 1.5 with `#param` in the prologue would bind to template parameters. To prevent collisions, `#param` is strictly restricted to the template prologue before any macro definitions or body content. Outside the prologue, `#param` is rejected at compile time.
5. **Candidate Directive Alternatives (Requirement 9)**: If an application contains an unmodifiable legacy macro named `#macro(param ...)`, evaluated alternatives include:
   - `#template_param(Type $var)`: Completely unreserved, highly explicit, zero collision probability.
   - `#declare(Type $var)`: Clean verb, unreserved in standard Velocity.
   - `#vt:param(Type $var)`: Namespaced directive, future-proof against any custom macro collision.
   Because `#param` is strictly restricted to the template prologue, `#param` remains the primary recommendation, with `#template_param` as the reserved architectural fallback.

### 3.2 Velocity Compatibility Analysis (Requirement 8)
- **Untyped Existing Templates**: 100% compatible. Any template without `#param` parses and executes with identical AST, IR, and runtime output.
- **Execution of Typed Templates in Apache Velocity**: Apache Velocity without Viet Template does not recognize `#param(...)` and would treat it as an unrecognized directive (emitting literal text or throwing an unknown directive error depending on configuration). This is expected and documented: **existing templates remain compatible, while 1.5 typed templates require the Viet Template 1.5 parser**.

### 4.2 Rejection Rationale
- **Candidate B**: Rejected because the colon `:` separator is unnatural in Java/Spring/Quarkus server-side templates, and the leading `$` already serves as an unambiguous identifier delimiter.
- **Candidate C**: Rejected because lack of enclosing parentheses makes parser synchronization and error recovery fragile, especially when generic angle brackets `<>` interact with HTML body markup.
- **Candidate D**: Rejected as the sole mechanism because forcing separate `.vt-schema.json` files for every template creates massive authoring friction and decouples type contracts from template source.
- **Candidate F**: Rejected for core type intelligence because comments are advisory and cannot reliably enforce compile-time error reporting or strict AST lowering.
- **Candidate E (Hybrid Bridge)**: Adopted in conjunction with Candidate A, where inline `#param` acts as authoritative template-level contract, while companion schemas provide external defaults via 4-tier precedence.
- **Placement Rule Qualification**: Typed declarations are **strictly restricted to the template prologue**. Restricting to the prologue guarantees zero interference with body control flow, avoids mid-template type redefinitions, preserves clean single-pass parsing, and allows immediate symbol table initialization before body AST traversal.

## 5. Parameter Declaration Semantics & Template Invariants

The qualification establishes definitive semantics for template parameters in M45B:
1. **Required vs Optional**:
   - A parameter without a default value is **required** by default (`#param(Employee $employee)`).
   - A parameter with a default value expression is **optional** (`#param(int $page = 1, String $sort = 'desc')`).
   - Nullable parameters are explicitly marked with `?` (`#param(Manager? $manager)`).
2. **Template Prologue Invariant**:
   - `#param` directives **MUST appear exclusively in the template prologue** (preceding any HTML markup, body text, or output directives).
   - Encountering `#param` after body content triggers a fatal compile error: **VTLS2111 (`PARAM_NOT_IN_PROLOGUE`)**.
3. **Duplicate Declaration Semantics**:
   - Declaring the same parameter variable twice in a template prologue triggers a fatal compile error: **VTLS2108 (`DUPLICATE_PARAM`)**.
4. **Macro Parameter Scoping**:
   - `#param` declares root template parameters only.
   - Macros retain independent, locally scoped parameters (`#macro(badge $label) ... #end`). Macro bodies may read root parameters from the outer template scope, but macro parameters do not pollute root template parameter contracts.
5. **Include & Parse Scoping**:
   - Parameter contracts are **strictly template-scoped**.
   - `#parse` and `#include` directives execute within their own parameter contracts; child templates do not implicitly inherit parent `#param` declarations without explicit context passing.
6. **Runtime Output Invariant (Requirement 42)**:
   - `#param(...)` directives render **exactly zero characters** (empty string). They produce zero runtime output and zero runtime side effects.

## 7. Canonical Internal Type Model & Type Algebra

The canonical type model maps into the existing sealed `VType` algebra in `viet-template-language-vtl`:
- `VType.PrimitiveType`: `int`, `long`, `boolean`, `double`, `float`, `byte`, `short`, `char`
- `VType.ClassType`: Java classes (e.g. `String`, `Employee`, `Manager`, `List<T>`, `Map<K, V>`)
- `VType.ArrayType`: Component types (`T[]`)
- `VType.DynamicType`: Intentionally dynamic receiver; suppresses strict type diagnostics
- `VType.NullType`: Literal `null`
- `VType.UnionType`: Flow-refined union types from conditional branching
- `VType.ErrorType`: Error sentinel suppressing secondary cascade diagnostics

### Dynamic vs Unknown Distinction (Requirement 16)
- **`DynamicType`**: Explicitly dynamic receiver. Emits no compile-time errors and dispatches dynamically at runtime via inline-cached call sites.
- **`UnknownType`**: Undeclared receiver in strict closed-schema mode. Emits `VTLS:2101` (`UNRESOLVED_ROOT`) to alert developers to undeclared variables.

### Generics & Wildcards (Requirements 25, 26)
- Full Java constraint solving is deferred. A pragmatic erasure + element metadata model is adopted:
  - `List<Employee>` exposes element type `Employee` to `#foreach`.
  - `Map<String, Address>` exposes key type `String` and value type `Address`.
  - `List<? extends Employee>` conservatively resolves element type to upper bound `Employee`.
  - `List<? super Employee>` and `List<?>` resolve element type to `Object` / `DynamicType`.
  - Type variables (`T`, `E`) degrade conservatively to `Object` / `DynamicType`.

## 10. Security Sandbox & Threat Model Analysis

### 10.1 Fail-Closed Invariant & Zero Privilege Escalation (Requirements 29, 30)
Static type declarations provide **zero additional runtime or reflection authority**. The security sandbox enforces strict compile-time and runtime invariants:
- **Compile-Time Rejection**: Accessing `$employee.class`, `$employee.getClass()`, `$employee.wait()`, `$employee.notify()`, or dangerous runtime classes (`ClassLoader`, `Thread`, `Runtime`, `ProcessBuilder`) emits diagnostic **`VTLSEC:2401` (`SECURITY_DENIED`)**.
- **Information Leak Protection**: Denied methods and classes are excluded from typo suggestion candidate sets. If a user enters `$employee.clas`, the compiler will not suggest `class`.
- **Runtime Dynamic Linker Parity**: `LinkerAccessPolicy.standard()` enforces identical method and class denials at runtime call sites, ensuring complete defense-in-depth across AST interpreter, IR interpreter, dynamic PIC linker, and GraalVM native binary execution.
