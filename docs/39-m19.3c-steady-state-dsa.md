## Status and scope

This phase follows the rule: remove work before making work faster. Correctness, security,
lifecycle ownership, and maintainability remain higher priorities than isolated benchmark scores.

Baseline results below are exploratory qualification runs (one fork, two warmups, three

## Current architecture and cost classification

| Operation | Lifetime classification | Baseline behavior | Decision |
|---|---|---|---|
| AOT registry discovery | engine/generation invariant | Once during engine construction | Keep |
| Precompiled class construction and wrapper metadata | engine/generation invariant | Repeated by every `get()` | Prepare once per engine |
| Compiler/profile/security key fragments | engine invariant | Re-derived on warmed lookup | Removed from precompiled warmed lookup; runtime-cache path deferred |
| Source and macro fingerprints | generation invariant | Checked on runtime-compiled lookup | Preserve until invalidation semantics are proven |
| `RenderBudget`, counting output, execution frames | render specific | Fresh per render | Keep request-local |

The execution backend (IR or AOT) remains independent from the caller thread model. Rendering is
synchronous and caller-thread-bound.

## Engine-level benchmark

`EngineSteadyStateBenchmark` separates:

1. retained `Template.render`,
2. warmed `engine.get(id)` followed by render,
3. full `engine.render(RenderRequest, output)`, and
4. the source-free precompiled AOT registry path.

Every workload has a realistic fresh `StringTemplateOutput` mode and a thread-confined retained
output diagnostic mode. The retained mode is not reported as the application-only result.

### Accepted candidate: engine-scoped precompiled AOT preparation

The generated compiled-template contract is immutable and thread-safe. Generated instances have no
request-specific instance fields; request context, output, budgets, and frames remain invocation
local. The engine now constructs one wrapper and compiled instance per discovered template per
engine generation. No static/global cache or additional synchronization was introduced.

| Runtime / output | Baseline ns/op | Candidate ns/op | Time change | Baseline B/op | Candidate B/op | Allocation change |
|---|---:|---:|---:|---:|---:|---:|
| Java 21 / realistic | 225.751 | 103.602 ± 1.496 | -54.1% | 952.010 | 624.002 ± 0.002 | -34.5% |
| Java 21 / retained diagnostic | 216.585 | 96.329 ± 1.293 | -55.5% | 768.010 | 440.002 ± 0.002 | -42.7% |

The candidate exceeds both the throughput/time and allocation acceptance thresholds on the directly
affected path while simplifying warmed lookup. Java 25 scalar replacement is stronger than Java 21,
so Java 21 still reports request-lifecycle allocations around the full engine call.

## JFR and source audit findings

The source-backed audit found these remaining generation-invariant costs:

- IR engine rendering runs `IrOptimizer.optimize` again on every render.
- IR rendering rebuilds `HashMap<String, IrFunction>` and the root slot layout per render.
- Every IR macro call recomputes its function slot layout and uses string-map dispatch.
- The second optimizer invocation cannot simply be deleted: global macros are merged after the first
  engine optimization. The correct boundary is macro merge, final optimization, final verification,
  then immutable preparation.
- AOT uses compiler-known direct macro methods already, but allocates `Object[]` arguments.
- Loop plans are currently metadata only. Neither backend consumes them.
- Arrays materialize an `ArrayList` in IR and AOT; ranges materialize boxed `Integer` lists in both;
  IR additionally drains a caller-supplied `Iterator` into a list before traversal.

The JDK 25 engine-level JFR follow-up confirms the prepared-IR candidate rather than relying only on
source inspection. In the representative IR engine request recording, `IrOptimizer.optimizeWithStats`
accounted for 4.69% of sampled CPU by itself, while optimizer-created `Object[]`, list iterators,
`MergeTextConstantsPass`, `IrDynamicDispatch`, and `LinkedHashMap` objects represented the dominant
allocation classes. The combined optimizer/preparation family is therefore material even though no
single helper uniformly exceeds 5%. The AOT and IR recordings reported no contention-by-site events
and no pinned-virtual-thread events. These short recordings rank candidates; they are not used as
standalone performance claims.

## Correctness, security, lifecycle, and concurrency

- Repeated precompiled lookups return the same prepared template within one engine.
- Separate engines receive distinct prepared wrappers, preserving engine policy/lifecycle ownership.
- Access policy, render limits, strict references, escaping, and output counting remain on the same
  render path.
- Prepared instances are not stored in static state. Their generated class and classloader references
  remain bounded by the engine generation.
- Virtual threads are used only as a caller-side compatibility/stress model, not as an internal
  rendering optimization.

## Rejected or deferred experiments

- A current-generation `ConcurrentHashMap<TemplateId, PreparedTemplateEntry>` was not added. The
  precompiled path could delete its obvious repeated work without adding a second lookup structure;
  runtime-compiled source/macro freshness still requires stronger invalidation evidence.
- Macro fingerprint caching was not added. Its current repository polling behavior detects library
  changes without explicit invalidation, so a generation cache needs a proven freshness contract.
- Dense function IDs, slot reuse, metadata elision, primitive specialization, and custom structures
  remain deferred until representative profiles attribute enough end-to-end cost.
