| Operation | Lifetime classification | Baseline behavior | Decision |
|---|---|---|---|
| AOT registry discovery | engine/generation invariant | Once during engine construction | Keep |

| Compiler/profile/security key fragments | engine invariant | Re-derived on warmed lookup | Removed from precompiled warmed lookup; runtime-cache path deferred |

synchronous and caller-thread-bound.

## M19.3c.2 — Prepared IR Execution — COMPLETE & FROZEN

### Baseline and boundary decision

The pre-change warmed engine path was:

```text
cached IrTemplate
  -> VtlInterpreter.render
  -> IrOptimizer.optimize (including IrVerifier)
  -> build HashMap<String, IrFunction>
  -> IrSlotLayout.layout(root)
  -> allocate request frame
  -> on each macro: IrSlotLayout.layout(function)
  -> execute
```

The engine already constructs one shared `VtlInterpreter` and one engine-scoped
`LinkedReferenceAccess`; neither was created per cached render. The repeated work was structural IR
preparation, not interpreter/linker construction. The second optimizer was necessary because global
macros were composed after the first local-template optimization.

The accepted boundary is:

```text
compile generation
  -> lower
  -> preliminary local optimization
  -> merge global macros and remap constants
  -> final optimization and verification
  -> prepare root layout, function lookup, and function layouts
  -> store immutable executable in CompiledTemplateHandle

warmed IR render
  -> create request ExecutionContext/frame/budget
  -> execute prepared root and function metadata
```

Raw `IrTemplate` interpreter entry points retain prepare-on-call behavior for compatibility. Dynamic
`#parse` and `#evaluate` sources are necessarily compiled and prepared per invocation; a small
request-local lazy overlay holds only functions introduced by those dynamic sources. The immutable
base lookup and all layouts for the cached generation are shared safely.

### Preparation lifetime decisions

| Operation | Previous lifetime | New lifetime | Why safe / request dependent? |
|---|---|---|---|
| Final `IrOptimizer.optimize` and `IrVerifier` | Per cached render | Once after global macro composition | Depends only on final immutable IR; not request dependent |
| `IrSlotLayout.layout(template)` | Per cached render | Once per compilation generation | Derived only from final root structure |
| Function lookup map | Rebuilt per cached render | Immutable map per generation; `Map.of()` for zero functions | Function precedence and local shadowing are final after composition |
| `IrSlotLayout.layout(function)` | Per macro invocation | Once per function per generation | Derived only from immutable function structure |
| `ExecutionContext`, `ExecutionFrame`, budget and dynamic-function overlay | Per render | Unchanged | Request mutable state; never stored in prepared metadata |

All prepared state is reachable only through the existing compilation handle. Cache invalidation,
engine close, or generation turnover therefore releases it without a static, global, or thread-local
cache. The prepared executable captures the existing engine-owned reference-access object and does
not create a second linker.

## M19.3c.3 — LoopPlan-Driven Iteration Specialization — COMPLETE

### Baseline, plan audit, and semantic boundary

Baseline SHA was `dfc6755`; the accepted production implementation is `0192a47`, with correctness
tests in `d3f5f19` and the benchmark harness in `c995d84`. The source audit found six plans:
`ARRAY`, `LIST_INDEXED`, `ITERABLE`, `ITERATOR`, `RANGE`, and `DYNAMIC`.

Before this phase both backends ignored the plan at loop execution. IR copied arrays into an
`ArrayList`, eagerly drained caller iterators, and materialized ranges as boxed lists. AOT consumed
caller iterators directly, but copied arrays and materialized ranges. Map iteration was and remains
the underlying map's values iterator. Generic `Iterable` was and remains its standard iterator.

The compiler classification is now conservative:

| Plan | Static proof | Execution after M19.3c.3 |
|---|---|---|
| `ARRAY` | IR type is an array | Constant-state reflective array iterator; no list/backing-array copy |
| `LIST_INDEXED` | Static class implements both `List` and `RandomAccess` | Standard iterator retained; indexing rejected below |
| `ITERABLE` | Static class implements `Iterable` | `Iterable.iterator()` |
| `ITERATOR` | Static class implements `Iterator` | Caller iterator directly; no eager drain |
| `RANGE` | Source expression is a VTL range | Overflow-safe constant-state counter iterator |
| `DYNAMIC` | Shape is not proven | Runtime classifier with direct iterator/iterable/map/array paths |

Range recognition now precedes the lowered expression's array type. Previously that ordering made
the explicit `RANGE` plan unreachable. Likewise, a plain `List` no longer claims indexed execution;
only a statically proven `RandomAccess` class receives `LIST_INDEXED`, preventing a future O(N^2)
LinkedList path.

The iterator semantic investigation found an existing backend inconsistency: AOT already streamed
the supplied iterator while IR eagerly drained it. IR now follows the AOT behavior. Tests with an
observable iterator prove that rendering is interleaved with `next()`, and `#break` after the second
element performs exactly two `next()` calls rather than draining the source. Metadata still uses
only `hasNext()` lookahead and does not consume the next element. Iterator ownership is unchanged;
the engine does not close caller iterators.

### Candidate decisions

| Candidate | Previous algorithm | Result | Decision |
|---|---|---|---|
| Reference/primitive arrays | Array -> `ArrayList` -> iterator | Deletes O(N) retained temporary storage; one request-local iterator | **ACCEPT** |
| Caller iterator | IR: drain -> `ArrayList`; AOT: direct | IR becomes one-pass and stops immediately on break | **ACCEPT** |
| Ascending/descending range | Boxed `ArrayList<Integer>` before body | Overflow-safe counter; O(N) retained temporary storage becomes O(1) | **ACCEPT** |
| Generic iterable | `iterable.iterator()` | Already the simplest JDK algorithm | **KEEP** |
| Map | `map.values().iterator()` | Preserves value and underlying order semantics | **KEEP** |
| RandomAccess indexing | `ArrayList.Itr` | Raw J25 diagnostic: about 0.23 us indexed versus 0.45 us iterator at N=1000, but real rendering is 70–95 us and iterator allocation is scalar-replaced | **REJECT — below end-to-end relevance** |
| Cursor hierarchy | None | Would add allocation/dispatch and duplicate simple JDK iteration | **REJECT — not prototyped into production** |

No foreach metadata, scope-map, frame-slot, macro-dispatch, or cache representation changed. Range
cardinality uses `long`, rejects oversized ranges before output, and terminates safely at
`Integer.MIN_VALUE`/`Integer.MAX_VALUE`. Boxing of values that must enter object-valued VTL context
remains; primitive specialization is explicitly outside this phase.

## M19.3c.4 — Request-Scope Representation & Dynamic Lookup DSA — COMPLETE

### Root cause and scope architecture

Baseline SHA was `128604e`. M19.3c.1, M19.3c.2, and M19.3c.3 remain **COMPLETE &
FROZEN**. The investigation did not begin with a replacement map. It traced the four request-local
storage tiers: compiler-assigned `ExecutionFrame` slots, stacked lexical `LocalScope` maps,
render-local `templateVariables`, and the caller `RenderContext`.

The pre-change IR foreach path had two independent redundancies:

1. `pushForeachScope` created a temporary two-entry `HashMap`, then `LocalScope` allocated another
   map and copied the two entries.
2. Each iteration wrote the item and `$foreach` from `InterpretedFrame.setLocal` into both slots and
   the top scope, then `updateLoopVariable` wrapped and wrote both values to the same scope again.

Macro invocation likewise built an engine-owned binding map and immediately copied it into a second
map. Public `pushScope(Map, boolean)` still copies caller bindings, preserving its ownership and
later-mutation behavior. Engine-created macro maps now have an internal ownership-transfer path.

`templateVariables` contains only non-null `EvaluationValue` instances because all writes flow
through `ExecutionContext.set`; its lookup therefore uses one `get` probe with Java `null` as the
internal absent signal. Root `RenderContext` retains `contains` plus `get`, because its public
contract distinguishes absent from defined-null. Arbitrary public scope maps retain the general
`containsKey` path, so Java-null caller values are not silently reinterpreted. `isolateSet` remains
stored but is not consulted by current lookup or assignment code; it was documented as dormant and
not removed in this performance phase.

Observed scope shapes explain why no custom telemetry was needed in production: foreach starts at
exactly two entries (item and metadata); benchmark macro scopes cover 0, 1, 2, 4, 8, and 16
parameters; nested fixtures cover depths 1, 2, 4, and 8. The retained loop fixture performs one
scope push/pop per render, two initial puts, two updates per iteration after the change, and no
body-local remove/reinsert. Dynamic evaluate/parse synchronization remains untouched.

### Accepted and rejected candidates

| Candidate | Result | Decision |
|---|---|---|
| Direct foreach construction | Deletes the temporary map, its table/nodes, and the destination copy | **ACCEPT** |
| Expected-size JDK map | `HashMap.newHashMap(2)` for foreach and exact macro binding cardinality | **ACCEPT** |
| Engine-owned macro bindings | Transfers only maps created solely for the current invocation; public copy semantics remain | **ACCEPT** |
| Template-variable single probe | Safe non-null internal-value invariant; defined-null remains an `EvaluationValue` singleton | **ACCEPT** |
| Duplicate slot/scope writes | One wrapper and one scope mirror per binding instead of two | **ACCEPT** |
| Lazy `templateVariables` | Saves at most one small map while complicating the public `templateVariables()` identity/mutability path | **REJECT** |
| `SmallLocalScope` | Post-change HashMap nodes/tables are about 0.15% of sampled allocation | **REJECT — no prototype retained** |
| Dynamic mirror elision | Higher semantic risk around `#evaluate`, `#parse`, macros, and body content after the simple fixes solved structural allocation | **DEFER** |

No custom map, tombstone state, pool, `ThreadLocal`, synchronization, or new prepared-template flag
was introduced.

## JFR and source audit findings

The source-backed audit found these remaining generation-invariant costs:

- IR engine rendering runs `IrOptimizer.optimize` again on every render.
- IR rendering rebuilds `HashMap<String, IrFunction>` and the root slot layout per render.
- Every IR macro call recomputes its function slot layout and uses string-map dispatch.
- The second optimizer invocation cannot simply be deleted: global macros are merged after the first
  engine optimization. The correct boundary is macro merge, final optimization, final verification,
  then immutable preparation.
- AOT uses compiler-known direct macro methods already, but allocates `Object[]` arguments.
- Loop plans are currently metadata only. Neither backend consumes them.
- Arrays materialize an `ArrayList` in IR and AOT; ranges materialize boxed `Integer` lists in both;
  IR additionally drains a caller-supplied `Iterator` into a list before traversal.

The JDK 25 engine-level JFR follow-up confirms the prepared-IR candidate rather than relying only on
source inspection. In the representative IR engine request recording, `IrOptimizer.optimizeWithStats`
accounted for 4.69% of sampled CPU by itself, while optimizer-created `Object[]`, list iterators,
`MergeTextConstantsPass`, `IrDynamicDispatch`, and `LinkedHashMap` objects represented the dominant
allocation classes. The combined optimizer/preparation family is therefore material even though no
single helper uniformly exceeds 5%. The AOT and IR recordings reported no contention-by-site events
and no pinned-virtual-thread events. These short recordings rank candidates; they are not used as
standalone performance claims.

## Correctness, security, lifecycle, and concurrency

- Repeated precompiled lookups return the same prepared template within one engine.
- Separate engines receive distinct prepared wrappers, preserving engine policy/lifecycle ownership.
- Access policy, render limits, strict references, escaping, and output counting remain on the same
  render path.
- Prepared instances are not stored in static state. Their generated class and classloader references
  remain bounded by the engine generation.
- Virtual threads are used only as a caller-side compatibility/stress model, not as an internal
  rendering optimization.

## Rejected or deferred experiments

- A current-generation `ConcurrentHashMap<TemplateId, PreparedTemplateEntry>` was not added. The
  precompiled path could delete its obvious repeated work without adding a second lookup structure;
  runtime-compiled source/macro freshness still requires stronger invalidation evidence.
- Macro fingerprint caching was not added. Its current repository polling behavior detects library
  changes without explicit invalidation, so a generation cache needs a proven freshness contract.
- Dense function IDs, slot reuse, metadata elision, primitive specialization, and custom structures
  remain deferred until representative profiles attribute enough end-to-end cost. Request-scope map
  work is the leading post-loop hypothesis, not an implementation in M19.3c.3.

## M19.3c.5 — Value Representation & Foreach Observability

Status: **COMPLETE & FROZEN**. M19.3c.1 through M19.3c.4 remain complete and frozen.

### Allocation attribution and semantic boundary

The M19.3c.4 post-change JFR ranked `EvaluationValue` at 70.43% and `ForeachMetadata` at
26.87% of sampled allocation. The relevant loop performed two logically avoidable allocations per
iteration: immutable `ForeachMetadata`, plus the non-null `EvaluationValue` wrapping it. A third
`EvaluationValue` represented the loop item and remains required by the current frame/context
boundary.

Lowering now performs a conservative, linear traversal of each loop body. The existing optional
`IrLoop.loopStateLocal` is absent only when `$foreach` cannot be observed. Direct loads retain it;
`#evaluate`, `#parse`, and macro calls are dynamic hazards and retain it; a nested loop requiring
metadata conservatively propagates the requirement to its enclosing loop. This existing IR signal
feeds both prepared IR and AOT, so neither backend performs a render-time observability check and no
public IR shape or per-loop side table was added.

For a proven metadata-free IR loop, execution skips parent lookup, metadata construction, metadata
wrapping, metadata slot writes, and the `$foreach` scope binding. The loop item, budget checks,
break handling, iteration counters, and lexical cleanup remain unchanged. When metadata is
observable, the existing immutable snapshot object is retained without mutation or reuse.

### Post-change profile and value-representation decision

The J25 metadata-free IR JFR contains no `ForeachMetadata` allocation sample. The remaining
`EvaluationValue` samples resolve directly to `IrInterpreter.executeLoop` wrapping the loop item.
Other visible allocations include the body-block/list iterator and request frame. The exact hot
wrapper is therefore known, but removing it is not a localized array substitution: static local
reads currently return `EvaluationValue`, dynamically visible locals mirror the same wrapper into
`ExecutionContext`, and undefined/null behavior is consumed throughout expression evaluation.

`Object[]` plus an undefined sentinel was therefore **REJECTED without a production prototype**.
Making it effective would spread sentinel awareness or boundary materialization across expression,
scope-mirroring, macro, parse/evaluate, and public `ExecutionFrame` paths. That semantic surface is
disproportionate to the remaining end-to-end cost, especially because Java 25 AOT already removes
the corresponding allocation. `EvaluationValue[]` and the exact three-state model remain intact.

### Correctness and rejected alternatives

Focused lowering tests cover metadata-free loops, direct metadata access, nested parent
propagation, macro, parse, and evaluate hazards. IR/AOT execution tests cover metadata-free output,
nested parent metadata, and captured immutable snapshot state. Existing differential, strict/null,
scope, break, security, concurrency, and bytecode-verification suites remain the semantic backstop.
The bytecode invariant now correctly expects one fewer local for a metadata-free loop.

Mutable metadata reuse, metadata/value pools, `ThreadLocal` caches, primitive wrapper subclasses,
preview value classes, partial metadata objects, and lazy runtime metadata were rejected. No
internal virtual threads, executor, synchronization, pooling, or new classloader-owned global state
was introduced. Virtual threads remain a caller-side host execution model.

Fresh evidence does not justify a raw/tagged frame refactor or another M19.3c production phase.
M19.3c stops after this metadata-elision change unless a future representative profile identifies a
new material hotspot.
