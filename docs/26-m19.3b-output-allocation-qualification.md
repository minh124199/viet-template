## 2. OUTPUT ARCHITECTURE AUDIT

An exhaustive audit of the Viet Template output subsystem covered all relevant classes:
- [`TemplateOutput.java`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-api/src/main/java/io/github/minh124199/viettemplate/api/TemplateOutput.java): The core SPI interface defining `write(CharSequence)`, `write(CharSequence, int, int)`, `write(char)`, `writeInt(int)`, `writeLong(long)`, `writeDouble(double)`, `writeBoolean(boolean)`.
- [`StringTemplateOutput.java`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-runtime/src/main/java/io/github/minh124199/viettemplate/runtime/StringTemplateOutput.java): In-memory UTF-16 character output backed by an expandable `StringBuilder` (default capacity $128$).
- [`Utf8OutputStreamTemplateOutput.java`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-runtime/src/main/java/io/github/minh124199/viettemplate/runtime/Utf8OutputStreamTemplateOutput.java): Streaming output writing directly to a `java.io.OutputStream` using an internal `byte[8192]` buffer. Encodes UTF-8 via direct bit manipulation into the buffer.
- [`WriterTemplateOutput.java`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-runtime/src/main/java/io/github/minh124199/viettemplate/runtime/WriterTemplateOutput.java): Character stream adapter delegating to `java.io.Writer`.
- [`NumberFormatting.java`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-runtime/src/main/java/io/github/minh124199/viettemplate/runtime/NumberFormatting.java): Utility methods for fast primitive formatting to byte arrays and writers.
- [`HtmlTextEscaper.java`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-runtime/src/main/java/io/github/minh124199/viettemplate/runtime/HtmlTextEscaper.java): Automatic HTML entity escaper (`&`, `<`, `>`, `"`, `'`).
- [`BytecodeRuntimeBridge.java`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-vtl-interpreter/src/main/java/io/github/minh124199/viettemplate/vtl/compiler/bytecode/BytecodeRuntimeBridge.java): The runtime dispatch bridge executing compiled bytecode instructions for literals, variables, expressions, and loops.

### Key Architectural Discoveries:
1. **Static Literals Are Already Zero-Allocation in AOT**: In `IrConstant`, static strings are pre-encoded into UTF-8 `byte[]` arrays at template compile time. In `BytecodeRuntimeBridge.writeConst`, when the output is `Utf8OutputStreamTemplateOutput`, the bridge retrieves `constant.utf8Bytes()` and writes them directly without any runtime character-to-byte transcoding or array allocations.
2. **Dynamic String UTF-8 Encoding Is Stream-Direct**: `Utf8OutputStreamTemplateOutput.write(CharSequence)` iterates through characters and writes UTF-8 code points directly into its internal buffer. It does **not** call `String.getBytes(StandardCharsets.UTF_8)`, avoiding temporary array creation.
3. **Severe Primitive Formatting Allocation Leak**: In `NumberFormatting.java` (lines 99 and 132), `formatInt` allocates `byte[] temp = new byte[11]` and `formatLong` allocates `byte[] temp = new byte[20]` on **every single call** before copying to the target array!
4. **HTML Escaping Substring Allocation Leak**: In `HtmlTextEscaper.java` (lines 54, 71, 79), escaping calls `input.subSequence(last, i)`. When `input` is a `String`, `subSequence` delegates to `String.substring()`, allocating a new heap `String` for every segment between HTML special characters.
5. **Double-Buffering & Harness Allocation Penalty**: In unpooled benchmarks, constructing `new Utf8OutputStreamTemplateOutput(baos)` allocates `new byte[8192]`, while `new ByteArrayOutputStream(1024)` allocates `new byte[1024]`. For small/medium templates producing $<1\text{ KB}$ of output, allocating $9.2\text{ KB}$ of buffers per render completely distorts the streaming throughput.

## 3. CURRENT OUTPUT IMPLEMENTATIONS

| Implementation | Backing Store | Internal Buffer Size | Primitive Fast-Path | Static Literal Path | Dynamic String Path |
|---|---|---|---|---|---|

| **`WriterTemplateOutput`** | `Writer` | None (delegates) | Uses `NumberFormatting.formatInt(..., char[])` | Writes pre-computed `String` | Writes `CharSequence` directly |

## 4. QUALIFICATION METHODOLOGY (`VT-PERF-M19.3B-QUALIFICATION-1`)

The qualification suite is implemented in [`StreamingOutputQualificationBenchmark.java`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-benchmarks/src/main/java/io/github/minh124199/viettemplate/benchmarks/output/StreamingOutputQualificationBenchmark.java) and executed under JMH:
- **GC Allocation Profiling**: Enabled via `-prof gc`, tracking `gc.alloc.rate.norm` ($B/\text{op}$), `gc.alloc.rate` ($\text{MB/s}$), and GC event counts.
- **JFR Call-Tree Profiling**: Enabled via `-prof jfr`, capturing `jdk.ObjectAllocationSample` and `jdk.ObjectAllocationInNewTLAB` events with full execution stack traces.
- **Output Strategies Evaluated**:
  1. `STRING`: Production [`StringTemplateOutput`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-runtime/src/main/java/io/github/minh124199/viettemplate/runtime/StringTemplateOutput.java) (allocated per render).
  2. `UTF8_STREAM_NEW`: Production [`Utf8OutputStreamTemplateOutput`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-runtime/src/main/java/io/github/minh124199/viettemplate/runtime/Utf8OutputStreamTemplateOutput.java) with `new ByteArrayOutputStream(1024)` (allocated per render, unpooled baseline).
  3. `UTF8_STREAM_REUSED`: Production `Utf8OutputStreamTemplateOutput` reusing a pre-allocated stream and buffer via thread-local state (isolating pure write-path cost from setup allocation).
  4. `UTF8_POOLED`: Diagnostic prototype [`DiagnosticPooledUtf8Output`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-benchmarks/src/main/java/io/github/minh124199/viettemplate/benchmarks/output/prototype/DiagnosticPooledUtf8Output.java) acquiring an $8\text{ KB}$ buffer from a bounded pool (max 64 buffers = $512\text{ KB}$ global cap) and releasing on `close()`.
  5. `UTF8_DIRECT_BYTE`: Diagnostic prototype [`DiagnosticDirectByteOutput`](file:///home/lynguyen/current_source/viet-template-repo/viet-template-benchmarks/src/main/java/io/github/minh124199/viettemplate/benchmarks/output/prototype/DiagnosticDirectByteOutput.java) writing into an expandable direct byte array, eliminating `ByteArrayOutputStream` synchronization overhead.

## 8. THROUGHPUT BY OUTPUT TYPE

Analysis of throughput patterns across output types:
1. **The Small-Template Deficit ($<1\text{ KB}$)**:
   In small templates (`staticAscii`, `scalarString`), `StringTemplateOutput` outperforms unpooled `Utf8OutputStreamTemplateOutput` by $3\times\text{--}13\times$. This gap is **almost entirely attributable to buffer instantiation**: allocating an unpooled $8\text{ KB}$ buffer for a 300-byte render imposes a heavy allocation and zeroing penalty. When the buffer is pooled or reused, streaming throughput increases by **$+100\%$ to $+150\%$**, narrowing the gap significantly.
2. **The Medium/Large Template Parity ($>5\text{ KB}$)**:
   In `foreachTable` (50 rows) and `macroCards` (20 cards), streaming output performs at direct throughput parity with `StringTemplateOutput` ($19,363\text{ vs }20,699\text{ ops/s}$ on JDK 17; $21,709\text{ vs }23,771\text{ ops/s}$ on JDK 25).
3. **Direct Byte Output Advantage in Sustained Documents**:
   In `largeDocument` ($\approx 64\text{ KB}$), `DiagnosticDirectByteOutput` achieves $32,553\text{ ops/s}$ compared to $19,285\text{ ops/s}$ for `UTF8_STREAM_NEW` ($+68.8\%$ gain) by avoiding `ByteArrayOutputStream` synchronization and internal re-copying.

## 11. BUFFER GROWTH ANALYSIS

- In `Utf8OutputStreamTemplateOutput`, the internal buffer is fixed-size (`byte[8192]`). It **never resizes or expands**. When full, it invokes `flushBuffer()`, writing the accumulated bytes to the underlying `OutputStream` and resetting `count = 0`.
- Therefore, there is **zero buffer growth allocation** inside `Utf8OutputStreamTemplateOutput`.
- Buffer expansion allocations observed in JFR occur strictly within caller-supplied expandable streams (e.g. `ByteArrayOutputStream.ensureCapacity`).
