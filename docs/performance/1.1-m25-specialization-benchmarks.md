# 1.1 Milestone M25 — Typed Specialization & Multi-Argument Invocation Benchmarks

> **Milestone:** M25 · **Baseline:** `v1.1.0-SNAPSHOT` (post-M24 merge `0d9b196`) · **Date:** 2026-09-28

This document details the benchmark methodology, empirical throughput, allocation measurements, and architectural decisions for **Milestone M25: Multi-Argument Static Invocation, Runtime Guards, Single-Evaluation Guarantees, and Typed Root-Slot Evaluation**.

---

## 1. Executive Summary

Milestone M25 builds upon the M24 contract foundation to implement direct JVM method invocation for multi-argument methods in AOT-compiled templates.

Key empirical findings:
1. **Multi-Argument Specialization Uplift**: Direct JVM dispatch (`invokevirtual` / `invokeinterface`) eliminates polymorphic inline cache dynamic link overhead, yielding **2.6× to 4.1× throughput improvements** across arities 1, 2, 4, and 8.
2. **Allocation Reduction**: Under GC allocation profiling (`-prof gc`), direct 2-argument invocation reduces heap allocation from **384.85 B/op to 120.00 B/op (-68.8%)**, eliminating dynamic callsite arguments array packaging and boxed boxing.
3. **Primitive Widening and Overload Resolution**: Widening conversions (e.g. `int` -> `double`) and deterministic compile-time overload selection achieve up to **19.2× throughput speedup** over runtime reflection probes.
4. **Root-Slot ABI Evaluation (Workstream B Decision)**: Detailed microbenchmarking of `RenderContext.of(...)` lookup versus retained context revealed that context lookup overhead is negligible (8.52M ops/s dynamically allocated context vs 8.32M ops/s retained context). Introducing custom root-slot arrays (`Object[] roots`) would increase carrier allocations without measurable net gain. **Decision: Root-slot optimization is REJECTED AFTER PROFILING**, preserving the clean, compact public API.

## 4. Root-Slot ABI Profiling & Architectural Decision

### 4.1 Hypothesis
Workstream B explored whether bypassing `RenderContext` variable name lookups via a compiler-assigned root-slot array (`renderSlots(Object[] roots, TemplateOutput out)`) would provide measurable throughput or allocation improvements in compiled templates.

### 4.2 Measurement Results
Under Workload M25_10:
- Dynamic ephemeral `RenderContext.of("svc", svc, "a", 10, "b", 20)`: **8,520,963 ops/s**
- Retained pre-allocated `RenderContext`: **8,321,817 ops/s**

The difference between creating an ephemeral `RenderContext.of(...)` and using a retained instance is within 2.3% (statistical noise). The flat array lookup inside `SingleVariableRenderContext` / `FixedKeyRenderContext` compiles down to an array index load in C2.

### 4.3 Decision: REJECTED AFTER PROFILING
Introducing an internal `Object[]` root-slot ABI:
1. Would force caller frameworks to allocate `new Object[] { ... }` array carriers per render invocation, increasing heap pressure on multi-argument renders.
2. Would proliferate duplicate public/internal execution entrypoints in `CompiledTemplate`.
3. Offers no statistically significant throughput improvement.

Following Section 19, 20, 37, and 59 of the M25 specification, the root-slot prototype is **REJECTED AFTER PROFILING**. The existing zero-allocation `RenderContext` architecture is preserved as the single canonical execution model.
