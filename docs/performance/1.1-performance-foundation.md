# 1.1 Performance Foundation

> **Baseline established:** 2026-09-26 · **GA reference:** `v1.0.0` (`b951021e9975b8e8103b2402dc244b32a96afaa8`)

> **Historical planning record:** This document captured the initial 1.1 performance plan before the 1.1 release. Its proposed mandates and candidate rankings are not current work status. The final two-profile release qualification is complete in [`benchmark-evidence/1.1.0/`](../../benchmark-evidence/1.1.0/) and documented in [`comparative-benchmarks.md`](comparative-benchmarks.md).

This document defines the performance foundation for the Viet Template 1.1 development cycle. It records the canonical 1.0.0 performance baseline, identifies the principal throughput hotspots discovered during GA qualification, ranks candidate optimizations for 1.1, and establishes the measurement framework for regression prevention.

No benchmark-driven optimizations are introduced in this document. This is a planning and evidence-anchoring artefact. All 1.1 optimizations will be proposed, prototyped, benchmarked, and reviewed as separate PRs after this foundation is accepted.

---

## 1. Executive Summary

Viet Template 1.0.0 ships with a competitive interpreter-mode (`Viet-IR`) throughput across all eight standard workloads relative to legacy engines (Velocity, Thymeleaf), and an AOT-compiled mode (`Viet-AOT`) that closes the gap to purpose-built precompiled engines (jte, Qute) for static and scalar workloads. The 1.1 cycle has two performance mandates:

1. **Regression prevention**: No 1.1 change regresses any 1.0.0 baseline workload beyond the policy threshold (10% default, 15% for C03).
2. **Targeted throughput improvement**: Identify and address the top three Viet-IR bottlenecks — reflective property dispatch, foreach iterator allocation, and typed slot propagation.

## 3. Hotspot Analysis

Profiling evidence from M18 qualification benchmarks and architectural review identifies three primary bottleneck categories.

### 3.1 Reflective Property Dispatch (C03 — `deepPropertyChains`)

**Evidence**: C03 achieves 194K ops/s on J21, roughly 4.6× slower than Viet-AOT (909K) and 21.8× slower than jte (4.23M) on the same workload. The J21→J25 improvement is negligible (<1%), confirming the bottleneck is not JIT-sensitive.

**Root cause**: The dynamic linker uses polymorphic `MethodHandle` call sites with per-invocation reflection probes when the cache is cold or invalidated. For deep chains (4+ levels), each property traversal may incur a full reflection probe and `MethodHandle` construction.

**Candidate improvement for 1.1**:
- Implement inline cache warming across the call site chain on first render
- Introduce a typed propagation tier that encodes resolved `MethodHandle` chains in the compiled representation, bypassing per-node lookup on subsequent renders
- Target: Reduce C03 latency by 30–50% on J21 (to ≥280K ops/s)

**Risk**: Medium. Inline caches interact with classloader lifecycle and security policies. Requires TCK validation.

### 3.2 Iterator Allocation in Foreach Loops (C05–C07)

**Evidence**: C05 (`smallTableForeach`, 5 items) achieves 114K ops/s vs Qute 356K and jte 1.16M. The GC allocation profile shows ~10,320 B/op for C05 Viet-IR vs ~6,331 B/op for Qute and ~1,608 B/op for jte.

**Root cause**: Each foreach iteration allocates a new `VelocityIteratorAdaptor` wrapper and a new scope `Frame` to hold the loop variable. The outer frame chain traversal for each `$item` access copies context state rather than projecting it.

**Candidate improvement for 1.1**:
- Reuse the iterator adaptor across loop iterations (reset pattern rather than re-allocate)
- Pre-allocate loop frames as a stack-local resource per foreach node
- Target: Reduce C05 allocation from 10,320 B/op to ≤4,000 B/op; expect 40–60% throughput improvement

**Risk**: High. Frame sharing must not break nested foreach or recursive macro semantics. Requires explicit scope isolation tests.

### 3.3 Typed Slot Propagation in Scalar Rendering (C02, C04)

**Evidence**: C02 (`scalarVariables`) achieves 1.18M ops/s on J21, with 1,848 B/op allocation. Viet-AOT achieves 1.26M ops/s with only 1,824 B/op — the gap is small but the allocation path is identical, suggesting the IR interpreter overhead is principally in object boxing of primitive values.

**Root cause**: The current IR interpreter boxes all context values to `Object` when placing them into the execution frame. Integer and boolean values are auto-boxed at every frame push and unboxed at every property reference.

**Candidate improvement for 1.1**:
- Implement a typed slot frame that carries `int`, `long`, and `boolean` primitives without boxing where the static type is known (from the `public-surface-classification` type annotations)
- For template variables inferred as numeric at parse time, emit specialized instruction paths that operate on the primitive stack slots
- Target: Reduce C02 allocation from 1,848 B/op to ≤1,200 B/op; throughput improvement secondary

**Risk**: Low-to-medium. Typed slots are already partially implemented (M18 slot frame architecture). This extends them to the scalar rendering hot path. Requires the API compliance verifier to confirm no ABI changes.

## 4. Candidate Optimization Ranking for 1.1

| Rank | Optimization | Workload Impact | Risk | Expected Gain |
|------|-------------|-----------------|------|---------------|
| 1 | Iterator allocation reuse (foreach) | C05, C06, C07 | High | 40–60% throughput ↑ |
| 2 | Inline call-site chain warming (reflection) | C03 | Medium | 30–50% throughput ↑ |
| 3 | Typed slot primitives (scalars) | C02, C04 | Low-Medium | 20–35% allocation ↓ |
| 4 | UTF-8 buffer reuse extension | All (allocation) | Low | 5–10% allocation ↓ |

All candidates must be benchmarked using `CHARACTERIZATION` protocol before PR and `RELEASE_QUALIFICATION` protocol before any release. Use `scripts/compare-benchmark-baseline.py` to verify no regression in unrelated workloads.

## 5. Regression Prevention Framework

### 5.1 Per-Commit Policy

Every commit that touches the following paths must include a `CHARACTERIZATION` benchmark run result or a documented rationale for why performance is unaffected:

- `viet-template-runtime/src/main/java/**`
- `viet-template-vtl-interpreter/src/main/java/**`
- `viet-template-language-vtl/src/main/java/**`

### 5.2 Pre-Release Policy

Every release candidate must include a `RELEASE_QUALIFICATION` benchmark run using `scripts/compare-benchmark-baseline.py` against `config/performance/1.0.0-baseline.json` for both `J21-G1` and `J25-G1` profiles. The comparison must exit 0 before the release tag is applied.

```bash
# Pre-release regression check (both profiles required)
python3 scripts/compare-benchmark-baseline.py \
  --results benchmark-evidence/current/comparative-J21-G1.json \
  --profile J21-G1

python3 scripts/compare-benchmark-baseline.py \
  --results benchmark-evidence/current/comparative-J25-G1.json \
  --profile J25-G1
```

### 5.3 Regression Thresholds

| Workload | Default Threshold | Override | Rationale |
|----------|:-----------------:|:--------:|-----------|
| C01–C02, C04–C08 | 10% | — | Standard regression gate |
| C03 deepPropertyChains | — | **15%** | Higher JIT variance on reflective call sites |

New workloads added in 1.1 must be added to the baseline with `CHARACTERIZATION` evidence and approved thresholds before the 1.1 release.

## 6. AOT Comparative Position

For reference, the 1.0.0 AOT (`Viet-AOT`) throughput is not tracked as a regression baseline in `config/performance/1.0.0-baseline.json` because AOT compilation is a deployment-time decision, not a runtime invariant. Historical AOT benchmark evidence remains in [`benchmark-evidence/m18/`](../../benchmark-evidence/m18/); current comparative measurements are reported in [`comparative-benchmarks.md`](comparative-benchmarks.md).

The 1.1 performance work focuses exclusively on the IR interpreter path (Viet-IR) because that is the path taken at development time, in Spring Boot DevTools restart mode, and for templates added at runtime.
