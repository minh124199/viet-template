## 1. STARTING STATE

Prior to this validation milestone, the **M19.3b Streaming Output Allocation & UTF-8 Formatting** initiative completed four successive production improvements:
1. **M19.3b.1**: Zero-allocation direct primitive decimal formatting (`NumberFormatting.formatInt` and `formatLong`), eliminating temporary 11-byte and 20-byte heap arrays.
2. **M19.3b.2**: Zero-allocation HTML text escaping via range forwarding in `TemplateOutput.write(CharSequence, int, int)` and `HtmlTextEscaper`, eliminating substring allocations.
3. **M19.3b.2.1**: SPI contract hardening and `WriterTemplateOutput` non-String range write optimization via a lazy instance-owned scratch buffer.
4. **M19.3b.3**: Productionization of bounded UTF-8 stream-buffer reuse in `Utf8BufferPool` (capacity 16 = 128 KiB maximum retained payload, lock-free `AtomicReferenceArray<byte[]>`), integrated into `Utf8OutputStreamTemplateOutput` with single-owner confinement.

The M19.3b.3 production implementation was merged into `main` via PR #15 at commit `c122295d2f0789df06d8cfa37c3100f7bfd60644`.

## 2. WHY POST-MERGE VALIDATION WAS REQUIRED

While M19.3b.3 successfully merged, several critical engineering questions remained:
1. **Methodology Rigor**: The initial qualification measurements for M19.3b.3 utilized lightweight settings (1 fork, 2 warmups, 3 measurement iterations of 1s each). Authoritative benchmarking requires $\ge 3$ forks, $\ge 5$ warmups, and $\ge 10$ measurement iterations to eliminate fork-level JIT variance.
2. **Beyond Monitor Contention**: The observation of "0 JFR monitor contention events" did not prove the absence of contention because `Utf8BufferPool` uses lock-free atomic CAS scans (`AtomicReferenceArray`). Real multi-threaded concurrency scaling and pool saturation needed empirical validation.
3. **Lifecycle Contract & Integrator Safety**: The exact semantics of `close()` vs `flush()`, stream ownership, unclosed instance behavior, and exception handling required formal verification and clear documentation.
4. **Documentation Accuracy**: Historical qualification reports contained phrasing that conflated observed JMH allocation reductions with exact object header sizes. These required precise correction.
5. **Freeze Decision**: A rigorous qualification gate was needed to determine whether M19.3b could be permanently frozen.

## 5. LEGACY FRESH-BUFFER BASELINE

To isolate exactly one variable (fresh 8 KiB buffer allocation vs pooled buffer reuse), the benchmark suite defines `CURRENT_NEW`:
```java
// Instantiates Utf8OutputStreamTemplateOutput with bufferSize = 8191
// This bypasses the Utf8BufferPool (which strictly manages DEFAULT_BUFFER_SIZE = 8192)
// while executing identical encoding, formatting, escaping, and writing bytecodes.
try (Utf8OutputStreamTemplateOutput out = new Utf8OutputStreamTemplateOutput(baos, 8191)) {
  tpl.render(ctx, out);
}
```
In a 64-bit JVM with compressed OOPs, `new byte[8191]` occupies 16 bytes header + 8,191 bytes payload = 8,207 bytes, padded to an 8-byte boundary = **8,208 bytes**—identical to `new byte[8192]`. This provides an exact, zero-overhead legacy control.

---

## 6. PRODUCTION POOLED ARCHITECTURE

The production merged architecture in `Utf8BufferPool` consists of:
- A package-private final class holding an `AtomicReferenceArray<byte[]>` of length 16.
- Standard buffer size: `8192` bytes.
- Lock-free `tryAcquire()`: linear scan `0..15` using `getAndSet(i, null)`. Returns the first non-null buffer, or `null` if exhausted.
- Lock-free `release(byte[])`: verifies `buf.length == 8192`, linear scan `0..15` using `compareAndSet(i, null, buf)`. Returns `true` if deposited, `false` if rejected or full.
- Maximum retained payload: $16 \times 8,192\text{ bytes} = 131,072\text{ bytes} = 128\text{ KiB}$.
- Non-blocking fallback: When pool is exhausted, `Utf8OutputStreamTemplateOutput` allocates an unpooled `new byte[8192]` without blocking or parking.

## 12. COLD VS WARM POOL

- **Cold Pool**: On application bootstrap or after `resetForTesting()`, all 16 slots of `Utf8BufferPool` are `null`. The first 16 invocations encounter a pool miss and allocate a standard `new byte[8192]` buffer via fallback. Upon `close()`, these buffers populate the slots.
- **Warm Pool**: Once populated, steady-state renders acquire existing buffers with 0 array allocations.
- **Construction-Site Note**: Instantiation of `Utf8OutputStreamTemplateOutput` is **not universally allocation-free**; in steady state, the `Utf8OutputStreamTemplateOutput` instance itself is allocated (approx. 48 bytes), while the 8 KiB payload array allocation is completely eliminated.

---

## 13. POOL HIT/MISS BEHAVIOR

1. **Single-Thread Steady State**: 100% pool hits. A single thread leases slot 0, renders, and returns the buffer to slot 0 upon `close()`.
2. **Concurrency $\le 16$ Threads**: High hit rate ($>95\%$). Threads find unoccupied slots in the 16-slot array.
3. **Concurrency $> 16$ Threads (Saturation)**: The first 16 threads lease the pooled buffers; surplus concurrent renders encounter `null` during `tryAcquire()` and allocate fresh buffers via fallback. As renders close, buffers are re-deposited into vacant slots.

## 31. CLOSE LIFECYCLE AUDIT

Audit of `Utf8OutputStreamTemplateOutput.close()`:
```java
@Override
public void close() throws IOException {
  if (closed) {
    return;
  }
  try {
    flush();
  } finally {
    closed = true;
    byte[] b = this.buffer;
    this.buffer = null;
    if (isPooled && b != null) {
      Utf8BufferPool.release(b);
    }
    out.close();
  }
}
```
Closing the output performs three operations:
1. Flushes any remaining bytes in the buffer to the underlying stream.
2. Marks the output closed, nulls the local buffer reference, and returns the leased buffer to `Utf8BufferPool`.
3. Closes the wrapped underlying `OutputStream`.

---

## 32. FLUSH-ONLY LIFECYCLE AUDIT

`flush()` writes buffered data to the underlying stream and invokes `out.flush()`. **`flush()` does NOT release the pooled buffer.** This preserves standard streaming semantics where callers flush intermediate chunks (e.g. HTTP chunked transfer) before continuing to write to the same output instance.

---

## 33. CLOSE-EXCEPTION BEHAVIOR

Stress Test 11 (`testProductionOutputCloseExceptionGuaranteesBufferRelease`) confirmed that if the underlying `OutputStream` throws an `IOException` during `flush()` within `close()`, the `finally` block guarantees that:
1. The buffer is released back to `Utf8BufferPool`.
2. The output is marked `closed` and its buffer field is set to `null`.
3. Subsequent write attempts throw `IOException("Output is closed")`.

---

## 34. DOUBLE-CLOSE / USE-AFTER-CLOSE

1. **Double-Close Idempotency**: Calling `close()` multiple times is safe and idempotent. The underlying stream is closed exactly once, and the buffer is released to the pool at most once.
2. **Post-Close Write Protection**: All write methods (`write(CharSequence)`, `write(char)`, `writeUtf8(...)`, `writeInt(...)`, `writeLong(...)`, `flush()`) begin with `ensureOpen()`. Attempting to write after close immediately throws `IOException("Output is closed")`.

---

## 35. STALE-BYTE NON-OBSERVABILITY

Buffer reuse does **not zero out the entire 8 KiB array** between leases (which would waste CPU cycles). Instead:
- When an output leases a buffer, its write cursor starts at `position = 0`.
- All writes advance `position`.
- When flushing or closing, only bytes in `0..position` are written to the stream.
- Unit Test `testStaleByteNonObservability` proved that rendering a 500-byte string followed by reusing the buffer for a 5-byte string results in an output stream containing strictly the 5 new bytes. Stale bytes from prior renders are mathematically unobservable.

## 40. FREEZE DECISION

### **Decision: `A. M19.3b FROZEN`**

**Rationale**:
1. **Authoritative Benefit**: Verified $+142.6\%$ speedup on tiny ASCII templates, $+79.2\%$ on Unicode, $+60.5\%$ on dynamic strings, $+73.5\%$ on HTML escaping, and $+21.1\%$ on medium templates with 0 regressions on large documents under authoritative 3/5/10 protocol.
2. **Deterministic Allocation Reduction**: Exactly 8,208 B/op eliminated across all 8 taxonomy workloads.
3. **High-Concurrency Safety**: Maintains $+63\%\text{--}+72\%$ speedups up to 32 concurrent threads oversubscribing pool capacity; non-blocking fallback operates with zero contention.
4. **Virtual-Thread Compatibility**: Zero thread pinning, zero `ThreadLocal`, and 100% data fidelity across 10,000 virtual-thread tasks.
5. **Lifecycle Hardening**: Confirmed idempotent double close, post-close write protection, guaranteed release on flush exception, and non-observable stale bytes.

**Freeze Policy**: The streaming output subsystem is now frozen. No further speculative output micro-optimizations or pool retuning shall be undertaken without concrete profiling evidence demonstrating output subsystem bottlenecking in real-world application workloads.
